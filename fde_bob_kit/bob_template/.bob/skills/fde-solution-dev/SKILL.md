# FDE ソリューション開発

業務観察で見えた課題から、現場で使われるアプリへ落とし込むための進め方です。
FDE の 4 つの動き「深く理解する → 早く解決する → 現場に定着させる → 知見を還元する」を一連で扱います。

## 共通ルール（全ステップで守る）

- 事実と推測を分ける。観察で確認していないことは「仮説」と明記し、不明点は推測で埋めずに質問する。
- 成果物は `docs/fde/` に Markdown で出力する（なければ作成）。既存ファイルは上書きせず、差分を示して確認する。
- コードを変更する前に、計画と影響範囲を示して承認を得る。
- 個人情報・機密・API キーを LLM・ログ・Git に渡さない。`.env` は読まない・出力しない。
- AI の出力を自動送信・自動確定する設計にしない。人が確認・承認する境界を必ず要件に含める。
- 最終判断（案の採否・プロトタイプの範囲）は人が行う。Bob は根拠付きの推奨までを出す。

## 手順

### Step 0: 入力の確認

次の 3 つを確認する。足りなければ質問して止まる。

1. 対象業務と利用者（誰の、どの業務か）
2. 観察で見えた課題とその根拠（観察メモ、ヒアリング、データ）
3. ソリューション案（1 つ以上）

### Step 1: 案の評価と絞り込み

[evaluation-criteria.md](evaluation-criteria.md) に従い、ゲート判定と採点を行う。

- 案が複数ある場合は比較表、推奨するプロトタイプ、理由を示す。
- 案が 1 つの場合も、ゲート判定と弱い観点の補強案を示す。
- 結果は `docs/fde/00_evaluation.md` に出力する。

### Step 2: 機能要件の一覧化

[requirements-template.md](requirements-template.md) の形式で `docs/fde/01_requirements.md` を作る。

- すべての要件を課題 ID に紐づける。紐づかない要件は削除候補として挙げる。
- 各要件の担い手を AI / 人 / システムに分ける。
- 優先度「必須」はプロトタイプの範囲だけにする。受け入れ基準は観測できる形で書く。
- 「範囲外」を必ず書く。

### Step 3: RAG 要否の判定

RAG とは、回答や判断の根拠を既存文書（FAQ・手順書・分類基準・過去チケット）の検索に求める方式を指す。

- **RAG ベースの場合**: サンプルアセットを参考にする。次の順に読み、再利用を優先して差分だけを新規に作る。
  1. `README.md`
  2. `Day2開発案内/サンプルアセットアプリ紹介.md`
  3. `openapi/helpdesk-api.yaml`
  4. `backend/src/helpdesk/` の `ports/` → `services/` → `api/`
  5. `data/seed/masters.json`（値の定義のみ）
  - サンプルアセットの場所が分からないときは、ユーザーに質問する。
- **RAG ベースでない場合**: サンプルアセットは読み込まず、そのまま Step 4 へ進む。構成パターン（ports/adapters、設定管理、テスト配置）が有用なときだけ参照する。

### Step 4: 必要リソースの一覧化と配置先の指定

[resource-placement.md](resource-placement.md) に従い、`docs/fde/02_resources.md` を作る。

- 要件 ID ごとに必要なリソースを挙げる。
- 配置先は必ず具体的なパスで書く。
- 「既存 / 要作成 / 要依頼」を区別する。IBM Cloud の環境など自分で用意できないものは「要依頼」とする。
- 秘密情報の配置先は `.env` のみとする。

### Step 5: 実装と検証

- 必須要件から、入力から出力まで通る最小の縦のスライスを 1 本先に動かす。
- 既存のコードパターンに合わせる。無関係な箇所は直さない。
- プロジェクトにあるテスト・Lint・型チェック（例: `make test` / `make lint` / `make typecheck`）を実行し、結果を報告する。
- AI の判定や生成を含む場合は、評価用データで [evaluation-criteria.md](evaluation-criteria.md) の「C. AI 品質」を測る。

### Step 6: 現場への定着と知見の還元

`docs/fde/03_adoption_and_learnings.md` に次を書く。

- **定着**: 現場向けの使い方 1 ページ、運用担当（文書や基準を誰が更新するか）、既存運用（Excel・電話など）からの移行手順
- **還元**: 汎化できた部分、次の現場でカスタマイズなしで使える部品、テンプレート化できる手順、失敗要因と学び

## 各ステップ完了時の報告

作ったもの（ファイルパス）、前提と仮説、未決事項、次にやることを短くまとめて報告する。

## 用語の補足

| 用語 | 簡単な説明 |
|---|---|
| FDE | 顧客の現場で、課題の理解から解決策の実装・定着までを一貫して進めるエンジニアの役割。 |
| 仮説 | 現時点の情報から立てた、検証が必要な見立て。観察済みの事実とは区別する。 |
| プロトタイプ | 解決策の価値や実現性を確かめるために作る試作品。完成品や本番運用を前提としない。 |
| 機能要件 | 利用者やシステムが「何をできる必要があるか」を表す条件。 |
| 受け入れ基準 | 要件を満たしたと判断するための、確認可能な条件。 |
| RAG | 関連文書を検索し、その内容を根拠としてAIに回答を作らせる方式。 |
| LLM | 入力された文章をもとに、回答などの文章を生成するAIモデル。 |
| Ports／Adapters | Portsは外部機能との接続ルール、Adaptersはそのルールに沿った具体的な接続実装。 |
| 縦のスライス | 画面や入力から処理・出力まで、最小限でも一連の流れが動く実装単位。 |
| Lint／型チェック | Lintはコードの書式や問題のある書き方を、型チェックはデータ型の不整合を検査する。 |
| 定着 | 作った仕組みが現場の業務へ組み込まれ、継続して使われる状態。 |
| 知見の還元 | 開発で得た成功・失敗や再利用可能な部品を整理し、別の案件でも使えるようにすること。 |
