## 4. 機能要件

| 要件 ID | 要件（〜できる） | 課題 ID | 担い手 | 優先度 | 受け入れ基準（観測できる形） | 必要リソース（02 の ID） |
|---|---|---|---|---|---|---|
| FR-001 | | P-01 | AI / 人 / システム | 必須 / 優先 / 任意 | | R-xx |

書き方のルール:

- 1 要件 1 文。「〜できる」で終える。
- 受け入れ基準は数・時間・有無など確認できる形にする（例: 評価チケット 20 件のうち、根拠付きで提案できた割合）。
- 担い手が「AI」の要件には、対になる「人が確認・修正する」要件を置く。
- 「必須」はプロトタイプで必ず実現する範囲だけにする。迷ったら「優先」に下げる。

## 用語の補足

| 用語 | 簡単な説明 |
|---|---|
| トリアージ | 内容や緊急度を確認し、優先順位や担当先を振り分けること。 |
| RAG | 関連文書を検索し、その内容を根拠としてAIに回答を作らせる方式。 |
| 機能要件 | 利用者やシステムが「何をできる必要があるか」を表す条件。 |
| 非機能要件 | 性能、セキュリティ、運用など、機能以外に満たす必要がある品質条件。 |
| 受け入れ基準 | 要件を満たしたと判断するための、数値や結果で確認できる条件。 |
| 必須／優先／任意 | 必須はプロトタイプで必ず実現する要件、優先は重要だが時間に応じて判断する要件、任意は余裕があれば対応する要件。 |
| プロトタイプ | 解決策の価値や実現性を確かめるために作る試作品。完成品や本番運用を前提としない。 |
| 説明可能性 | AIなどが出した結果について、参照元や判断理由を人が確認できる性質。 |
| 範囲外 | 今回は実装・対応しないと明示した項目。スコープの拡大を防ぐために記録する。 |
